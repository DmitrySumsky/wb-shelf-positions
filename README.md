# 34. Позиции наших карточек в рекомендательных полках конкурентов (WB)

Облачная замена ручному прокликиванию через расширение **ТурбоМинимум RM**.
Раз в сутки снимает, на какой позиции наша карточка стоит в полке каждого конкурента,
и кладёт результат в Google-таблицу.

## Как это устроено

Разбор расширения (CRX v74, 27.07.2026) показал, что фича
`campaign-edit-competitor-recom-shelves-positions` дергает один публичный эндпоинт:

```
GET https://recom.wb.ru/recom/ru/common/v8/search
    ?query=<nmID КОНКУРЕНТА>        # артикул подставляется в поле поискового запроса
    &resultset=catalog&curr=rub&spp=30
    &ab_testing=false&suppressSpellcheck=false
    &page=N&dest=<регион>&appType=1
```

Ответ — упорядоченный список товаров полки. Позиция = индекс + 1.
**Авторизация не нужна**: `recom.wb.ru` и `card.wb.ru` отвечают без кук и токенов.
Антибот WBaaS стоит на `www.wildberries.ru`, но не на этих API-хостах — поэтому
задача решается в облаке, без браузера.

### Чем отличается от расширения

| | Расширение | Здесь |
|---|---|---|
| Глубина | только `page=1` (топ-100), дальше пишет «>300» | постраничный обход по `total` — реальные позиции 101+ |
| Запросов | на каждую пару «наш артикул × конкурент» | одна полка забирается один раз, в ней ищутся сразу все наши артикулы |
| Запуск | руками, по одному артикулу | GitHub Actions cron, раз в сутки |

Практический эффект глубины: в боевом прогоне 27.07.2026 по 12 конкурентам Артура
8 позиций из 12 оказались в диапазоне 101–148, то есть расширение показало бы «>300»
ровно там, где цифра нужнее всего.

Практический эффект переиспользования полки: объём работы **не зависит** от числа
наших карточек. 200 наших артикулов и 12 конкурентов — те же ~70 запросов, что и
для одного артикула.

## Откуда берутся артикулы

Из рабочей таблицы **«Аналитика цен WB»**, лист `Аналитика цен (wb кошелек)`:
колонка `A` — название товара (оно же группа), `B` — артикул, `C` — бренд.
Строки одной группы идут подряд.

Бренды `NATURI`, `SUNSHINE`, `Health Form`, `4ME` (константа `OUR_BRANDS`) считаются
нашими, остальные в группе — конкурентами. **Позиции считаются только внутри группы**:
наш магний ищется в полках конкурентов по магнию, а не по коллагену.

Ячейки без числового артикула (`отсутствует`, `пока нет`, `внести` и т.п.) пропускаются
и перечисляются в логе прогона — это не ошибка, а «у бренда нет такого товара».

## Параллельная ветка: конкуренты из поисковой выдачи (эксперимент, 29.07.2026)

Задача Артура: расширение Вячеслава Малых берёт «токен» из поиска WB и строит по
нему таблицу конкурентов — не по вручную отобранным артикулам, а по всей выдаче
по запросу. **Токен для этого не нужен**: выдача отдаётся публично тем же способом,
что полки и карточки.

```
GET https://search.wb.ru/exactmatch/ru/common/v12/search
    ?query=магний&resultset=catalog&curr=rub&spp=30
    &ab_testing=false&suppressSpellcheck=false
    &page=N&dest=<регион>&appType=1&sort=popular
```

Ответ `{metadata, products[], total}`; в товаре уже есть `id`, `brand`, `supplierId`,
`subjectId`, `name` — карточку отдельно тянуть не надо. 100 товаров на страницу,
глубина ровно **100 страниц (10 000 позиций)**, дальше `products` пуст.

Ветка сделана **рядом** с боевой, а не вместо неё: тот же обход полок, та же
раскраска и накопление дат, но источник конкурентов другой, а результат пишется
в листы с суффиксом **«(поиск)»**. Боевые «Матрица» / «Сводка» / «История» и
`snapshot.json` не затрагиваются.

**Как отбираются конкуренты по запросу:**

1. Выдача читается на глубину `max(топ-N, 1000)` — 1000 нужны, чтобы найти наши
   карточки: по «магний» наш Health Form стоит на 283-й позиции, при топ-200 он бы
   просто не нашёлся.
2. Наши артикулы берутся из выдачи по бренду (`OUR_BRANDS`), по одной — лучшей по
   позиции — карточке на бренд. Можно задать вручную колонкой в листе запросов.
3. Конкуренты — первые `топ-N` после трёх отсечек: чужая категория (`subjectId`
   отличается от преобладающего в первой сотне), больше 3 карточек одного продавца,
   наши собственные бренды. По «магний» это отбрасывает ~35% топа.
4. Что и почему отброшено — в лист «Отчёт (поиск)» и в лог, чтобы «взяли топ-100»
   нельзя было прочитать как «обошли всех конкурентов».

Список запросов живёт в листе **«Запросы (поиск)»** самой таблицы-приёмника
(запрос, топ-N, наши артикулы, фильтр по категории, вкл/выкл). Скрипт заводит лист
со стартовым набором, дальше правит его человек.

```bash
python to_sheets_search.py --creds <ключ SA> --sheet-id <ID приёмника>
python to_sheets_search.py --queries "магний,коллаген" --top-n 150 --dry-run
```

Расписания у ветки нет — только `workflow_dispatch`, пока прогоняем руками.

### Грабля выдачи: WB отдаёт чужой закэшированный ответ

Примерно каждый десятый запрос к `search.wb.ru` приходит в другом конверте —
`{metadata, state, version, params, data}` вместо `{metadata, products, total}`.
Внутри `data.products` лежит один посторонний товар (по запросу «магний» приезжал
Apple), а `params.dest` не тот, что просили. Читать оттуда товары нельзя — в
конкурентов попадёт мусор; считать это концом выдачи тоже нельзя — сбор молча
обрежется (у меня так и вышло: 500 позиций вместо 1000, без единой ошибки в логе).
Лечение — перезапрос той же страницы; если после четырёх попыток конверт всё ещё
чужой, страница помечается как неполученная и это видно в отчёте.

На `recom.wb.ru` (полки) такого поведения нет — 20 запросов подряд отдали
нормальный конверт, боевой контур править не пришлось.

## Цены поартикульно (лист «Цены», 30.07.2026)

Задача Егора: цены в том же формате, что позиции, — чтобы не проходить руками
по всем конкурентам несколько раз в день. `prices_to_sheets.py` снимает цену
у **всех** артикулов групп (наши + конкуренты) из публичного
`card.wb.ru/cards/v4/detail` (батч до 100, без авторизации, ~10 секунд на
320 артикулов) и пишет в лист «Цены» той же таблицы-приёмника:

- строки — артикулы группа за группой, наши первыми (голубая подсветка),
  колонка «Чей» (`наш` / `конкурент`) — для фильтра;
- колонки — даты, свежая слева (как в «Матрице»); строка 2 — **время последнего
  замера**;
- повторный прогон в тот же день обновляет колонку на месте — интрадей-запуски
  историю не раздувают;
- в таблицу идёт **цена с WB-кошельком** = `floor(цена карточки × 0.98)` — та же
  колонка, что менеджеры ведут в «Аналитике цен (wb кошелек)» (сверено с MPStats);
- раскраска — сравнение со вчерашней колонкой: подешевело — зелёным,
  подорожало — красным;
- состояния ячейки: `нет в наличии` (карточка есть, цены нет), `нет карточки`
  (артикул удалён с WB), `ошибка сбора` (батч не отдался — дырка замера).

Запускается дважды: шагом в ежедневном `shelves.yml` после позиций и отдельным
лёгким workflow `prices.yml` — его cron-job.org дёргает несколько раз в день.

## Книги брендов (04.08.2026)

У каждого бренда своя таблица в папке «Анализ конкурентов»: NATURI, SUNSHINE,
Health Form, 4ME. В книге один лист **«Полки»**, раскладка — из образца Артура
«Натури пример»:

```
A Товар | B Артикул конкурента | C Бренд конкурента | D ~ Выручка |
E Тип конкурента | F Прогрев | G Прогрев к-во | H.. даты, свежая СЛЕВА
```

Список конкурентов у всех брендов **общий** — различается только контрольная
карточка: при заведении листа строки бренда поднимаются в начало своей группы,
контрольной становится та, у которой «Тип конкурента» совпадает с типом группы
(тип группы = тип её первой строки в образце). В ячейке даты — позиция этой
карточки в полке строки; у самой контрольной строки — «N из M» (в скольких
полках группы нашлись).

**Строки ведёт человек.** Скрипт каждое утро читает лист и дописывает ТОЛЬКО
колонку за сегодня: добавленный руками конкурент начинает заполняться со
следующего прогона, ничего перенастраивать не надо. Разбор не привязан к буквам
колонок (границей служит первая колонка-дата, поля ищутся по названию), пустой
«Товар» наследует группу строки выше, пустая строка закрывает группу.

**Кнопка в книге.** Меню «Полки WB» → «Обновить сейчас» дёргает
`brand-shelves.yml` со своим брендом (сама таблица ничего не считает: обход
полок — это минуты). Код — `apps_script/`, заливка — `python deploy_button.py`;
токен GitHub в репозиторий не попадает (в `Code.gs` плейсхолдер, значение
подставляется при заливке из локального файла).

## Файлы

- `shelf_positions.py` — ядро: обход полок, поиск позиций, снапшот в JSON.
- `brand_shelves.py` — книги брендов: лист «Полки», колонка за сегодня.
- `vexor_shelves.py` — лист «Полки» в книге автохимии VEXOR.
- `deploy_button.py` + `apps_script/` — кнопка обновления в книге бренда.
- `.github/workflows/brand-shelves.yml` — прогон по кнопке (`--brand`).
- `to_sheets.py` — чтение групп из таблицы цен + запись результата.
- `prices_to_sheets.py` — цены всех артикулов групп → лист «Цены» (см. выше).
- `config.json` — плоский список артикулов для разовых прогонов ядра мимо таблиц.
- `.github/workflows/shelves.yml` — ежедневный запуск в облаке (позиции + цены).
- `.github/workflows/prices.yml` — интрадей-срез цен, только `workflow_dispatch`.
- `search_groups.py` — **ветка «поиск»**: конкуренты из выдачи WB по запросу.
- `to_sheets_search.py` — **ветка «поиск»**: запись в листы с суффиксом «(поиск)».
- `.github/workflows/shelves-search.yml` — ручной запуск ветки «поиск».

## Расписание

Боевой запуск — **08:00 МСК**, каждый день. Дёргает не родной `schedule` GitHub,
а cron-job.org (тот же аккаунт и тот же токен, что запускают ежедневный отчёт по
заказам в 07:30): POST на `.../workflows/shelves.yml/dispatches`, тело `{"ref":"main"}`.

Причина: расписание GitHub не обязано быть пунктуальным — 28.07.2026 запуск на
07:10 МСК реально стартовал в 09:36. Полки надо снимать в одно и то же время
суток, иначе позиции соседних дней несравнимы (WB пересобирает выдачу в течение
дня сильнее, чем шум ±2).

Цены дополнительно обновляются **интрадей**: cron-job.org job 8186706 дёргает
`prices.yml` в 10:00–20:00 МСК каждые 2 часа (колонка дня перезаписывается на
месте, время замера — в строке 2 листа «Цены»).

## Запуск

```bash
pip install -r requirements.txt
python to_sheets.py --sheet-id <ID приёмника> --source-id <ID таблицы цен> --creds <ключ SA>
```

Собрать, но в таблицу не писать — добавить `--dry-run`.
Разовый прогон ядра по своему списку: `python shelf_positions.py --config config.json`.

## Что нужно настроить один раз

1. Создать таблицу-приёмник (создаёт человек: у сервисного аккаунта вне Workspace
   нет своей квоты Drive, сам файл он завести не может).
2. Расшарить приёмник **и таблицу цен** как «Редактор» / «Читатель» на сервисный аккаунт.
3. В репозитории задать секреты: `GCP_SA_JSON` (содержимое ключа), `SHEET_ID`
   (приёмник), `SOURCE_ID` (таблица цен).

Листы «Матрица», «Сводка», «История», «Цены» скрипт создаёт сам.

## Три состояния ячейки, которые нельзя путать

| В таблице | Что значит |
|---|---|
| число | позиция нашей карточки в полке |
| `—` | полка проверена целиком, нашей карточки в ней нет |
| `нет карточки` | артикул конкурента удалён/скрыт на WB (полка отдаёт пустое тело) |
| `ошибка сбора` | полку не удалось получить даже со второй попытки — **данных нет**, это не «нас там нет» |

Последние два в «Сводке» исключаются из знаменателя «Полок проверено».

## Ограничения, о которых стоит помнить

- **Позиции шумят на ±2** между соседними замерами: WB пересобирает полку на лету.
  Для трендов это нормально, но «точность до единицы» обещать нельзя — поэтому в
  историю пишется время замера.
- **Регион почти не влияет**: Москва / СПб / Краснодар / Екатеринбург дали
  113 / 111 / 113 / 113 на одной и той же паре. Снимать по всем регионам смысла нет.
- **Глубина полки ~475–490 товаров.** Если карточки нет и там, в матрице «—».
- WB может переименовать эндпоинт (в 2026-м уже исчезли `catalog-ads.*`,
  `rec-goods.*`, `similar-goods.*`). Если сбор вдруг вернёт пусто по всем полкам —
  первым делом проверять URL, а не логику.
- Первая страница штатно отдаёт **99** товаров, а не 100. Останавливать пагинацию
  по `len(products) < 100` нельзя — только по `total`.
- На несуществующий артикул полка отвечает **HTTP 200 с пустым телом** (не 404).
  Наивный `json.loads` падает на этом и выглядит как сетевой сбой — разводить явно.
