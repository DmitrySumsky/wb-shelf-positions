# 34. Позиции наших карточек в рекомендательных полках конкурентов (WB)

Облачная замена ручному прокликиванию через расширение **ТурбоМинимум RM**.
Раз в сутки снимает, на какой позиции наша карточка стоит в полке каждого конкурента,
и кладёт результат в Google-таблицу.

## Как это устроено

Разбор расширения (CRX v74, 27.07.2026) показал, что фича
`campaign-edit-competitor-recom-shelves-positions` дергает один публичный эндпоинт:

```
GET https://recom.wb.ru/recom/ru/common/v8/search
    ?query=<nmID КОНКУРЕНТА>        # артикул подставляется в поле поискового запроса
    &resultset=catalog&curr=rub&spp=30
    &ab_testing=false&suppressSpellcheck=false
    &page=N&dest=<регион>&appType=1
```

Ответ — упорядоченный список товаров полки. Позиция = индекс + 1.
**Авторизация не нужна**: `recom.wb.ru` и `card.wb.ru` отвечают без кук и токенов.
Антибот WBaaS стоит на `www.wildberries.ru`, но не на этих API-хостах — поэтому
задача решается в облаке, без браузера.

### Чем отличается от расширения

| | Расширение | Здесь |
|---|---|---|
| Глубина | только `page=1` (топ-100), дальше пишет «>300» | постраничный обход по `total` — реальные позиции 101+ |
| Запросов | на каждую пару «наш артикул × конкурент» | одна полка забирается один раз, в ней ищутся сразу все наши артикулы |
| Запуск | руками, по одному артикулу | GitHub Actions cron, раз в сутки |

Практический эффект глубины: в боевом прогоне 27.07.2026 по 12 конкурентам Артура
8 позиций из 12 оказались в диапазоне 101–148, то есть расширение показало бы «>300»
ровно там, где цифра нужнее всего.

Практический эффект переиспользования полки: объём работы **не зависит** от числа
наших карточек. 200 наших артикулов и 12 конкурентов — те же ~70 запросов, что и
для одного артикула.

## Откуда берутся артикулы

Из рабочей таблицы **«Аналитика цен WB»**, лист `Аналитика цен (wb кошелек)`:
колонка `A` — название товара (оно же группа), `B` — артикул, `C` — бренд.
Строки одной группы идут подряд.

Бренды `NATURI`, `SUNSHINE`, `Health Form`, `4ME` (константа `OUR_BRANDS`) считаются
нашими, остальные в группе — конкурентами. **Позиции считаются только внутри группы**:
наш магний ищется в полках конкурентов по магнию, а не по коллагену.

Ячейки без числового артикула (`отсутствует`, `пока нет`, `внести` и т.п.) пропускаются
и перечисляются в логе прогона — это не ошибка, а «у бренда нет такого товара».

## Файлы

- `shelf_positions.py` — ядро: обход полок, поиск позиций, снапшот в JSON.
- `to_sheets.py` — чтение групп из таблицы цен + запись результата.
- `config.json` — плоский список артикулов для разовых прогонов ядра мимо таблиц.
- `.github/workflows/shelves.yml` — ежедневный запуск в облаке.

## Расписание

Боевой запуск — **08:00 МСК**, каждый день. Дёргает не родной `schedule` GitHub,
а cron-job.org (тот же аккаунт и тот же токен, что запускают ежедневный отчёт по
заказам в 07:30): POST на `.../workflows/shelves.yml/dispatches`, тело `{"ref":"main"}`.

Причина: расписание GitHub не обязано быть пунктуальным — 28.07.2026 запуск на
07:10 МСК реально стартовал в 09:36. Полки надо снимать в одно и то же время
суток, иначе позиции соседних дней несравнимы (WB пересобирает выдачу в течение
дня сильнее, чем шум ±2).

## Запуск

```bash
pip install -r requirements.txt
python to_sheets.py --sheet-id <ID приёмника> --source-id <ID таблицы цен> --creds <ключ SA>
```

Собрать, но в таблицу не писать — добавить `--dry-run`.
Разовый прогон ядра по своему списку: `python shelf_positions.py --config config.json`.

## Что нужно настроить один раз

1. Создать таблицу-приёмник (создаёт человек: у сервисного аккаунта вне Workspace
   нет своей квоты Drive, сам файл он завести не может).
2. Расшарить приёмник **и таблицу цен** как «Редактор» / «Читатель» на сервисный аккаунт.
3. В репозитории задать секреты: `GCP_SA_JSON` (содержимое ключа), `SHEET_ID`
   (приёмник), `SOURCE_ID` (таблица цен).

Листы «Матрица», «Сводка», «История» скрипт создаёт сам.

## Три состояния ячейки, которые нельзя путать

| В таблице | Что значит |
|---|---|
| число | позиция нашей карточки в полке |
| `—` | полка проверена целиком, нашей карточки в ней нет |
| `нет карточки` | артикул конкурента удалён/скрыт на WB (полка отдаёт пустое тело) |
| `ошибка сбора` | полку не удалось получить даже со второй попытки — **данных нет**, это не «нас там нет» |

Последние два в «Сводке» исключаются из знаменателя «Полок проверено».

## Ограничения, о которых стоит помнить

- **Позиции шумят на ±2** между соседними замерами: WB пересобирает полку на лету.
  Для трендов это нормально, но «точность до единицы» обещать нельзя — поэтому в
  историю пишется время замера.
- **Регион почти не влияет**: Москва / СПб / Краснодар / Екатеринбург дали
  113 / 111 / 113 / 113 на одной и той же паре. Снимать по всем регионам смысла нет.
- **Глубина полки ~475–490 товаров.** Если карточки нет и там, в матрице «—».
- WB может переименовать эндпоинт (в 2026-м уже исчезли `catalog-ads.*`,
  `rec-goods.*`, `similar-goods.*`). Если сбор вдруг вернёт пусто по всем полкам —
  первым делом проверять URL, а не логику.
- Первая страница штатно отдаёт **99** товаров, а не 100. Останавливать пагинацию
  по `len(products) < 100` нельзя — только по `total`.
- На несуществующий артикул полка отвечает **HTTP 200 с пустым телом** (не 404).
  Наивный `json.loads` падает на этом и выглядит как сетевой сбой — разводить явно.
